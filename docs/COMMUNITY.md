# 贡献者、社区与可持续计划

代码仓库已公开于 [cocode199/requestdock](https://github.com/cocode199/requestdock)，并已启用 [Discussions](https://github.com/cocode199/requestdock/discussions) 与 [私密安全报告](https://github.com/cocode199/requestdock/security/advisories/new)。以下社区增长和收入安排仍是待执行计划；没有声称已建立 Discord、已招募维护者、已有赞助或真实用户。先把工作台用于真实项目，再决定社区是否值得扩大。

首批目标用户是已经维护少量 HTTP 回归集合、希望比较修改前后响应的个人开发者。用“同一个 JSON 集合，在页面调试，在 CLI 重跑，对比结果”演示一个完整任务。邀请试用时明确本版不兼容 Postman 脚本、不提供团队权限、不保证无损导入；记录用户选择继续使用或退出的具体原因。

## 前三个月

| 时间 | 行动 | 验收证据 |
| --- | --- | --- |
| 第 1–2 周 | 以已公开仓库为入口，检查 issue 模板和私密安全报告；发布 5 分钟本地演示与一个完整迁移案例 | 新用户从 README 能运行并重现演示；公开限制与迁移警告 |
| 第 3–4 周 | 邀请 5–10 位自愿试用者迁移自己的测试集合；在允许自荐的相关社区分享真实演示 | 至少 3 位独立用户持续两周使用；收集阻塞点而非索取 stars |
| 第 2 个月 | 公开每两周一次的变更记录；把真实缺陷整理成有验收条件的小任务；配对帮助首次贡献者 | 首个外部贡献从复现到合并可追踪；问题得到说明、修复或明确拒绝 |
| 第 3 个月 | 组织一次可异步参与的路线图讨论；邀请持续贡献者参与评审；公布预算和维护时间 | 至少两人能运行发布流程；维护负担和可用时间相匹配 |

不自动群发、不刷量、不买 star、不批量生成低质量 PR。对其他项目的问题，优先提交正确的上游修复，尊重其贡献规则和许可证。宣传内容必须展示实测工作流，并同时说明 Bruno / Hoppscotch 等成熟选择。

## 如何吸引贡献者

让首次贡献有明确的上下文：脱敏复现、预期结果、建议阅读的文件、测试命令和验收条件。提供真实有用的任务，如导入兼容性样本、响应比较边界、Windows 路径问题和键盘可访问性。文档、翻译、设计、问题复现也计入致谢。

[贡献指南](../CONTRIBUTING.md) 已提供三个候选起步任务：英文详细指南、可执行迁移样例、键盘完整流程验证。这些不是已经认领的任务或已确认缺陷。维护者应先检查重复工作、补充验收条件，再在仓库创建需要的 issue；不要批量发布空泛任务来制造活跃度。

维护者评审时解释原因；不把贡献者当免费交付队伍。贡献者没有承诺 SLA，任务无人认领时由维护者重排优先级。避免仅为增加 PR 数而拆分格式修改。每次发布按实际贡献致谢，并征求署名偏好。

## 治理

起步采用单一负责人加公开决策记录。涉及集合格式、插件 API 或安全边界的变化先写短提案，列出用户证据、迁移代价和维护成本。获得持续贡献和评审信任后再增加维护权限，启用受保护分支、最小 token 权限和可恢复的发布访问。

讨论遵循 [行为准则](../CODE_OF_CONDUCT.md)，围绕行为与事实，禁止骚扰、辱骂和发布他人私密信息。出现冲突时维护者先说明规则和处理理由；严重或重复违反者可以被限制参与。正式建社区前指定经本人同意的联络者，不虚构联系方式；现有 GitHub 举报入口属于平台渠道，不冒充维护者私密信箱。

## 观察健康度

| 指标 | 为什么关注 | 收集方式 |
| --- | --- | --- |
| 新用户首次成功运行耗时 | 是否真正易用 | 自愿试用反馈，不默认埋点 |
| 两周后仍运行回归的独立项目数 | 是否解决持续需求 | 自愿报告与匿名案例，拒绝虚构 |
| 首次回应与 PR 评审等待时间 | 维护者是否过载 | 仓库公开时间戳；同时报告中位数与长期积压 |
| 外部贡献复现率、合并后回归数 | 贡献质量 | 测试记录与发布缺陷 |
| 能独立发布/恢复的维护者数 | 避免单人风险 | 发布与恢复演练记录 |
| 每月支出和维护小时 | 是否可持续 | 月度预算表，不用 stars 代替收入 |

没有用户证据就不要扩招功能。连续两个月维护队列增加时，暂停新增大功能，先修复文档、测试和发布流程。

## 预算与收入

建议规划值为每月现金上限 **¥300**、维护时间 **每周 4–6 小时**，需由仓库拥有者确认；它们不是已发生费用、可用人员承诺或本计划对花费的授权。优先保持本地运行，不建立需要长期付费的公共代理；演示用合成数据录屏或本地示例。域名、CI 超额、托管和备份的实际报价在购买前核实，超预算时先停止非必要服务。

可持续方式按顺序验证：

1. 自愿赞助：明确资金用于安全修复、Windows 兼容和文档；有足够维护能力后再申请并公布真实赞助入口。
2. 有边界的付费服务：集合迁移、私有部署培训、插件开发、维护咨询；按交付内容报价，和社区缺陷修复分开排期。
3. 在证实需求后考虑托管服务：需要额外设计租户隔离、秘密管理、计费和运维，不能直接把当前单用户服务公开售卖。

已发布的 MIT 代码保持原许可证承诺。付款不保证不合适的功能进入核心。每季度公开支出、赞助用途、维护能力和下一阶段范围；收入不足时缩小支持面或提供归档/迁移路径，而非作无法兑现的支持承诺。
